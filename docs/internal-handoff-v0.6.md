# 내부·외부 연결 확인 및 내부 담당자 요청 v0.6

기준일: 2026-11-13. 내부 `e2c5648`, 공통 `fcdb992`의 소스와 `docs/external-handoff.md`를 기준으로 비교했습니다. 내부·공통 저장소는 수정하지 않았습니다.

추가 구현: 챗봇 없는 만남 일정 조율을 외부에 추가했습니다. 직원용 BFF와 현재 담당 관계 확인 API가 내부에 필요합니다. [일정 조율 구현·내부 연결 명세](meeting-scheduling.md)를 함께 확인해 주세요.

## 외부에서 반영한 사항

| 항목 | 반영 내용 |
|---|---|
| 증빙 종류 | 회원 화면에서 졸업증명서/재직증명서 선택. external-api → transfer-api → internal-api에 `kind=education/employment` 전달. 생략은 education, 다른 값은 422 |
| 상대 표시 | 동의 화면은 `counterpart_label` 사용. 관리자용 회원 코드를 표시 이름으로 사용하지 않음 |
| JWT | JWKS의 `use=sig`인 RSA 서명 키만 사용. 암호화용 키 제외, RS256·issuer·audience·azp 검증 유지 |
| 회원 상태 | 로그인 후 회원 상태를 먼저 조회하는 화면 추가. 활성 상태일 때만 업무 화면을 표시 |
| 탈퇴 | 사유 최대 200자, 본인 탈퇴 신청·상태 안내·본인 신청 철회 연결. 직원 처리 건은 철회 버튼을 표시하지 않고 내부 API에서도 최종 확인 |
| 삭제 완료 | 안내를 표시한 채 외부 서버 세션을 종료. 로그인 반복 이동을 만들지 않음. 토큰 갱신이 거부되면 기존대로 세션 폐기 |
| 서버 차단 | 상태 연동 활성화 시 기존 매칭·이용권·증빙·동의·목록·다운로드 요청도 최신 내부 상태 확인. 상태 API 실패를 active로 간주하지 않음 |
| 기존 기능 | 기존 유료 매칭 경로·예약/사용 횟수·반출 검사를 유지. 기존 증빙 클라이언트가 kind를 보내지 않아도 호환 |
| 실행 준비 | Start.ps1이 새 internal-admin 비밀값을 외부의 무시되는 `.local/internal-admin.env`에서 준비. 공통 .env나 기존 세션 키를 덮어쓰지 않음 |

## 새 전달 경로

서비스 토큰과 회원 access token을 함께 검증합니다. 회원 주체를 body의 user_id로 받지 않습니다. 브라우저의 변경 요청에는 기존 CSRF·Origin 검사를 유지합니다.

| 외부 BFF | 중계 | 내부 |
|---|---|---|
| GET /api/me/status | GET /api/internal/member-status | GET /api/internal/my-status |
| POST /api/me/withdrawal | POST /api/internal/member-withdrawal | POST /api/internal/my-withdrawal |
| POST /api/me/withdrawal/cancel | POST /api/internal/member-withdrawal/cancel | POST /api/internal/my-withdrawal/cancel |

`POST withdrawal` 입력은 `{reason?: string|null}`이며 최대 200자입니다. 취소는 빈 객체 `{}`입니다. 회원 상태 응답은 전달 문서의 네 상태를 사용하고, 예상하지 못한 개인정보 필드는 회원에게 다시 전달하지 않습니다. 탈퇴 사유·안내 본문·토큰은 감사 로그에 기록하지 않습니다.

## 함께 결정한 매칭 범위

사용자 결정: **기존 유료 매칭을 유지하고 내부 매칭·동의 자동 연계는 별도 합의 후 적용**합니다.

- 기존 `/api/me/matches`는 계속 `recipient_member_id + idempotency_key`를 받는 유료 신청입니다.
- 내부 문서에서 제안한 같은 주소의 `counterpart_member_id` 방식으로 덮어쓰지 않습니다.
- 기존 수락은 내부 `matches`·`consents`를 자동 생성하지 않습니다. 내부 상호 매칭도 외부 이용권을 자동 차감하지 않습니다.
- 별도 무료 매칭 POST 경로를 추가하지 않았습니다. 기존 수동 동의 등록·철회도 호환성을 위해 유지했습니다.
- 따라서 내부 문서의 "졸업증명서 통과 → 서로 매칭 → 동의 자동 생성" 시연은 이번 외부 수정만으로 완성되지 않습니다.

## 내부 담당자가 확인해야 할 항목

### 1. 정상 소개 파일의 정보 주체 값 불일치 — 정상 반출을 막는 항목

현재 내부 `business.py`의 `_detail_profile()`은 파일의 `member_pseudo_id`에 **실명**을 넣습니다. 하지만 `disclosure_check()`는 같은 이름의 응답 필드에 `members.pseudo_id`의 **회원 코드**를 돌려줍니다.

중계는 파일이 동의한 주체의 자료인지 확인하기 위해 두 값을 비교합니다. 예를 들어 파일은 실명이고 응답은 A-001이면 `profile_subject_mismatch`로 거부됩니다. 외부에서는 이 검사를 삭제하거나 이름/코드 어느 쪽이든 무조건 허용하는 우회를 넣지 않았습니다.

내부·중계가 함께 사용할 **주체 결합 계약**이 필요합니다. 권장 최종 방향은 표시 이름과 분리한 안정적인 member UUID에 파일을 결합하는 것입니다. 파일 형식·검사·응답의 버전을 함께 합의해야 하므로 외부에서 일방적으로 스키마를 바꾸지 않았습니다. 현재 4필드 형식을 유지하려면 최소한 파일과 disclosure 응답의 의미가 일치해야 하며, 실명만으로 주체 동일성을 보장한다고 보아서는 안 됩니다.

### 2. 기존 유료 매칭용 내부 API

기존 유료 매칭은 아래 두 내부 계약을 사용합니다. 이번 내부 버전에는 이 경로의 구현이 확인되지 않습니다. `my-matches`는 같은 응답이 아니며 필요한 user UUID·공개 결과·동의 검증을 대체할 수 없습니다.

- `POST /api/internal/matching-directory`: 기존 `docs/matching-api.md`의 자기/상대 최소 프로필과 업무용 UUID, 신청 가능 상태. 학력 심사 결과와 담당 소개 관계를 내부에서 확인해야 합니다. 회원 화면에 회원 코드·실명·학교·회사·연락처를 사전 공개하지 않아야 합니다.
- `POST /api/internal/matching-disclosures`: 매칭·방향별 공개 동의 범위에 맞는 검토 결과. 증빙 원본이나 미검토 개인정보를 반환하면 안 됩니다.

외부의 실제 내부 연결 모드는 미구현을 성공으로 대체하지 않습니다. 합성 실습 모드에서만 기존 유료 매칭을 독립 시험할 수 있습니다.

### 3. DB·시드·계정 준비

새 내부 이미지에는 최신 업무 DB 컬럼·테이블과 Keycloak 설정이 필요합니다. 기존 DB는 Docker 이미지 빌드만으로 업그레이드되지 않습니다. 내부 담당자의 마이그레이션 순서와 백업을 확인한 후 적용해야 합니다.

이번 작업은 실행 중인 컨테이너·DB·Wazuh 설정을 교체하지 않았고, 볼륨을 삭제하지 않았습니다. 기존 시험 자료를 없애는 `down -v`를 자동 실행하지 않습니다. 새 20명 시드와 기존 합성 member_c/d/e를 같은 업무 DB 회원으로 간주하지 않습니다.

## 활성화·호환성

- 기본 `compose.external.yaml`: `MEMBER_STATUS_CHECK=false`. 이전 내부 이미지와 기존 유료 매칭 실습의 실행을 보존하기 위한 전환 설정입니다. 새로운 탈퇴 신청/철회 쓰기 API는 이 상태에서 409로 거부됩니다.
- `compose.member-lifecycle.yaml` 추가: 두 외부 서비스에서 상태 확인 활성화. 비활성 회원의 기존 API 우회도 거부. 내부 상태 API·스키마 준비 후 사용합니다.
- 이 두 상태는 보안 수준이 같다는 의미가 아닙니다. **실제 탈퇴 기능 검증·사용 전에는 상태 확인을 활성화해야 합니다.**
- 합성 전용 `compose.matching-lab.yaml`은 내부 업무 DB에 없는 시험 계정을 사용하므로 상태 확인을 명시적으로 끕니다. lifecycle 파일과 혼합하지 않습니다.

실행 명령과 확인 순서는 [내부 변경 연동 실행 안내](internal-handoff-run-guide.md)에 있습니다.

## Wazuh

기존 두 공격·파일 무결성·매칭 권한 규칙과 로그 형식은 유지합니다. 내부 전달 문서에 맞춰 다음 규칙을 소스에 추가했습니다.

| ID | 조건 | 수준 |
|---|---|---|
| 100140 | internal-api / member_purge / error | 12 |
| 100141 | internal-api / evidence_delete / error | 10 |
| 100142 | internal-api / member_account_delete / error / not_member_account | 12 |

2026-11-13 새 세 규칙을 포함한 실제 규칙 엔진 시험 12건이 통과했고, 합성 이벤트 12건 모두 Manager 경보·Indexer 저장을 확인했습니다. 일괄 입력의 반복 경보는 100112 대신 100110으로 남았고, 별도 3초 간격 시험에서는 3번째 요청의 100112를 확인했습니다. smoke를 순차 입력으로 수정한 뒤 사용자 PC에서 prepare → smoke 재검증도 통과했습니다. 동시·일괄 입력 반복 탐지는 추가 확인이 필요합니다. 경보는 삭제 실패 관찰 결과이며 정상 삭제 완료나 공격 성공을 증명하지 않습니다.

## 이번 수정의 확인 결과

2026-11-13 일정 조율 추가 후 Python 109개·Node 화면 제어 9개 시험이 통과했습니다. 이후 smoke 진단 수정에 대해 관제 도구 시험 21개를 별도로 재실행해 통과했습니다. 기본/회원 상태 활성화/합성 실습의 Compose 병합 3가지와 JavaScript 구문·HTML ID/스크립트 참조도 확인했습니다. 사용자 기존 가상환경 대신 외부 `.local` 아래 별도 시험 패키지를 사용했습니다.
