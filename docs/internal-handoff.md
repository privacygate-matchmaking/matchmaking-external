# 외부 변경 정리 — 내부 담당 전달용

기준일: 2026-11-14. 유료 매칭·개별 공개 동의·직원 일정 조율을 기준으로 내부 연결을 수정하고, 소개 파일 주체 확인을 UUID로 통일했습니다. 이번에는 사용자 결정으로 필요한 내부 코드도 수정했습니다. 공통 privacygate 보안 코드·내부 README는 변경하지 않았습니다. 20명 계정 연결은 사용자 실행으로 적용했고, 이번 업무 흐름에는 새 DB 마이그레이션이 없습니다.

## 0. 먼저 할 일 (실행 환경)

- 기본 폴더·환경 파일·키 준비는 [실행 가이드](team1-run-guide.md)를 따릅니다. 자동 DB 초기화나 push는 하지 않았습니다.
- 내부 API와 외부/중계 이미지를 **함께 재빌드**해야 새 계약이 적용됩니다. 이전 내부 이미지와 새 중계를 혼합하지 않습니다.
- 사용자 PC의 matchmaking-20 DB에서 회원 20명과 member_001~member_020 계정 연결, member_003 증빙 제출·직원 학력 통과·외부 자격 갱신까지 확인했습니다. 새 매칭 반출은 아래 업데이트 후 확인합니다.
- 새로운 업무 DB 컬럼은 이번 수정에 추가하지 않았습니다. 최신 내부 스키마, 기존 중계 001/002 마이그레이션이 필요합니다.

## 1. 계정·로그인

JWKS 서명용 RSA 키만 사용하고 기존 회원 로그인·갱신·세션·CSRF를 유지합니다. 직원 일정 내부 확인은 서비스 토큰과 직원 토큰을 함께 검증하고, 업무 DB의 현재 활성·상담 역할을 재확인합니다. 이전 토큰의 역할만으로 일정 관리를 허용하지 않습니다.

## 2. 코드 규칙·표시

기존 동의 화면은 counterpart_label을 사용합니다. 실제 내부 매칭 후보도 관리자 코드나 실명 대신 나이·학력의 상대 설명을 사용합니다. 직원 일정 목록에서는 담당 회원의 코드·이름만 표시하며, 비담당 상대는 최소 설명만 보여줍니다. user_id(로그인 sub)와 member_id(업무 회원 UUID)를 구분합니다.

## 3. 새 20명 데이터·로그인 계정

내부 회원 20명과 기존 계정 4개 연결은 사용자 PC에서 적용을 확인했습니다. 추가 결정으로 전체 로그인 이름을 member_001~member_020으로 통일하는 도구를 준비했습니다. 기존 A-001~004의 로그인 UUID·비밀번호는 유지하고 이름만 변경하며, 나머지 16명은 신규 계정을 만들어 해당 내부 회원에 연결합니다. A-003의 새 로그인 이름은 member_003입니다.

회원 자료 20개를 다시 만들거나 삭제하지 않습니다. 직원 배정·소개 관계·학력 심사 조건은 그대로입니다. 내부 API는 이름이 아닌 user UUID로 신원을 확인하므로 계정 이름 변경 때문에 업무 로직을 다시 바꾸지 않습니다. Keycloak 계정과 내부 users/members 연결 설정을 함께 적용해야 합니다. `Update-Internal20Accounts.ps1` 실행 후 20명 연결 결과를 확인합니다. 사용자 실행 출력에서 20개 계정 준비와 내부 연결 적용을 확인했습니다. [적용 안내](internal20-start-guide.md)를 확인합니다.

## 4. 매칭 방식 (결정·코드 반영)

- 중계 matching_*가 이용권·신청·수락·공개 동의의 기준입니다. 내부 matches를 두 번째 기준으로 쓰지 않습니다.
- 유효 이용권으로 신청 → 상대 수락 → 정보 소유자가 항목·기간을 별도 동의합니다. 상호 수락만으로 원본·연락처를 공개하지 않습니다.
- 내부는 소개 관계·현재 활성·학력 심사 결과로 신청 가능한 후보를 제공하고, 실제 검토 완료된 텍스트 결과만 제공합니다.
- 구 내부 my-matches GET/POST/cancel은 409로 종료해 유료 제한을 우회하는 두 번째 매칭 경로를 막았습니다. 기존 기록·기존 동의는 삭제하지 않았습니다.
- 새 매칭 반출은 matching_grants의 실제 회원 동의 ID를 직접 참조합니다. 내부 consents에 동의를 복사하거나 자동 생성하지 않습니다. 직원이 별도로 발송을 요청하고 승인자가 승인합니다. 기존 consents 기반 반출 기록은 보존합니다.
- 현재 시험 상품 330만원·6개월·5회, 응답 기한 72시간을 유지합니다. 실제 결제는 없고 시험 결제는 명시적으로 활성화한 실습에서만 가능합니다.
- 신청 시 1회 예약, 수락 시 사용. 수락 전 취소·거절·만료는 예약 해제. 성사 후 종료는 사용 1회 유지, 변심·일정 변경·취소의 **추가 차감 없음**.

## 5. 증빙 종류·공개 결과

education/employment 선택·전달은 유지합니다. 내부 원본 보관·직원 심사 책임도 유지합니다. 새 matching-disclosures는 실제 passed 심사 기록의 시각을 사용하며, 동의한 profile/education/employment 중 제공 가능한 최소 텍스트만 반환합니다. 원본·실명·학교·회사·연락처는 반환하지 않습니다. 실제 심사 기록이 없는 시드의 확인 플래그만으로 reviewed_at을 만들어내지 않습니다. photo/contact/income/marital_status와 AI/OCR·자동 마스킹은 아직 제공하지 않습니다.

## 6. 기존 소개 자료 v2 — UUID 주체 연결

내부와 중계를 함께 수정했습니다.

```json
{
  "schema_version": 2,
  "member_id": "자료 주인의 업무 회원 UUID",
  "display_name": "표시용 실명",
  "age_band": "만 32세",
  "job_group": "직군",
  "introduction": "승인 대상 소개 내용"
}
```

위 예시는 UUID 자리 설명이며 실제 파일에는 유효 UUID를 넣습니다. 정확히 위 6개 키만 허용하고 schema_version은 정수 2, 나머지는 1~300자 문자열입니다.

- 내부 _detail_profile: 표시용 display_name과 자료 주인 member_id 분리.
- 내부 disclosure-checks: 실제 동의의 자료 주인 member_id와 expires_at을 반환.
- 중계: 파일 UUID·신청 UUID·동의 확인 응답 UUID를 대조. 신청·승인·다운로드에서 재검사하며 실명이나 회원 코드로 대체하지 않음.
- 기존 4필드 파일은 이름으로 UUID를 추측하지 않고 거부합니다. **내부에서 새 파일 생성→반출 신청→별도 승인**을 다시 해야 합니다. 기존 승인 건을 몰래 새 파일로 바꾸지 않습니다.
- 승인 파일의 버전·해시·수신자·기한 검사와 제한된 baseline/enforce 비교는 유지합니다.

## 7. 회원 탈퇴·안내

외부 코드는 유지합니다. 기본 호환 설정 MEMBER_STATUS_CHECK=false에서는 새 탈퇴 쓰기가 409입니다. 최신 내부 DB·API가 준비되면 compose.member-lifecycle.yaml로 활성화합니다. 합성 매칭 파일과 함께 쓰지 않습니다. 실제 새 20명 환경에서의 탈퇴·삭제 전 과정 시험은 아직 남아 있습니다.

## 8. 내부 API·직원 화면 (코드 연결 완료)

| 경로 | 반영 |
|---|---|
| POST /api/internal/matching-directory | 본인·소개 상대의 최소 프로필/UUID/현재 학력 조건 |
| POST /api/internal/matching-disclosures | 수신자·소개 관계·활성·심사 결과 확인 후 최소 텍스트 |
| POST /api/internal/matching-staff-checks | 현재 직원 권한·참여 회원 활성·소개 관계·담당 확인 |
| GET /api/matching/requests | 담당 가능한 성사 매칭 목록, 비담당 상대 이름 제외 |
| GET /api/matching/requests/{id}/meetings | 직원 일정 조회 BFF |
| POST 같은 meetings 경로 | 최대 3개 후보 제안 BFF |
| POST .../{proposal_id}/confirm 또는 cancel | 양쪽 응답 후 확정/취소 BFF |
| 내부 직원 화면 | 상담 역할의 만남 일정 관리 탭 연결 |

현재 계약은 **한쪽 이상 담당하면 조율 가능**, 담당 밖 회원의 개인 의견은 제외입니다. 양쪽 동의가 같은 후보에 있어야 확정합니다. 새 후보는 새 응답이 필요하고 재제안에 추가 차감은 없습니다. 이전 API 이미지에서는 새 메뉴를 숨기도록 capability 검사도 넣었습니다. 실제 브라우저·Keycloak·PostgreSQL에서 직원 발송까지 확인하는 시험은 남아 있습니다.

## 9. Wazuh

기존 규칙과 직전 실제 엔진 12건·순차 합성 수집 검증 결과는 유지합니다. 이번 내부 연결이 실제 웹에서 차단·탐지되는지는 재기동 후 추가 확인해야 합니다. 일괄 입력 반복 경보의 누락 한계도 남아 있습니다. [Wazuh 가이드](wazuh-run-guide.md)를 참고합니다.

## 10. 적용·검증 순서

1. 내부·외부 변경을 함께 검토하고 두 이미지를 재빌드합니다. DB 초기화는 별도 결정합니다.
2. 새 내부 데이터에서 상대 회원의 실제 로그인 계정 연결을 확인합니다.
3. 내부 연결 모드에서 후보/학력 조건·시험 이용권·수락·개별 공개 동의를 확인합니다. 시험 결제 활성화와 실제 PG는 구분합니다.
4. 직원 일정 탭에서 후보 제안 → 양쪽 회원 응답 → 직원 확정. 비담당 직원과 역할 변경도 거부되는지 확인합니다.
5. 소개 자료 v2를 새로 생성·신청·승인하고 정상 다운로드와 잘못된 UUID 거부를 확인합니다.
6. 실제 API 응답·파일과 Wazuh를 따로 확인합니다. 새 DB·브라우저 전체 확인 전에는 실제 전체 연동 완료라고 표현하지 않습니다.

챗봇·추가 취소 벌점·연락처 최종 승인 전달은 이번 수정에 포함하지 않았습니다. 상세 API는 [매칭](matching-api.md)·[일정](meeting-scheduling.md)에 있습니다.

## 2026-11-14 자동 검증 결과

내부·외부·관제 Python 142개, Node 화면 시험 9개 통과. 파일 UUID 불일치/표시 이름 독립, 구 매칭 우회 거부, 현재 직원 역할·담당 관계, 비담당 이름 제외, 최신 반려 후 과거 통과 결과 재사용 거부를 확인했습니다. 내부 DB는 시험 어댑터이며 이후 새 20명 DB·Keycloak·전체 서비스 기동과 계정 연결을 사용자 출력으로 확인했습니다. 실제 브라우저 업무 검증은 아직 남아 있습니다. GitHub 푸시는 사용자 확인 후 진행합니다.

20명 계정 변경 도구 시험 15개 통과. 실제 이름 통일·나머지 계정 생성·20명 DB 연결과 API 재시작을 사용자 출력으로 확인했습니다.


## 11. 매칭 현황·명시적 동의 기반 새 반출 (2026-11-14)

- 내부 `매칭·동의·일정` 및 담당 회원 상세에서 신청 대기·수락·거절·취소·종료와 각 방향의 최근 동의·발송 상태를 조회합니다. 기존 일정 API는 성사 매칭만 제공하는 계약을 유지합니다.
- `GET /api/matching/overview`: 내부 BFF → 중계. 현재 상담 역할·활성과 담당 관계를 내부에서 다시 확인합니다. 비담당 상대는 최소 설명으로 표시합니다.
- `POST /api/matching/releases`: 내부 BFF(CSRF/Origin) → 중계. 입력은 `{grant_id, scopes}`이며 회원이 동의한 profile/education/employment 중 직원이 명시적으로 선택합니다. 자료 주인을 담당한 직원만 요청할 수 있습니다.
- `POST /api/internal/matching-release-checks`: 중계 서비스 전용 내부 API. 현재 회원 활성·소개 관계·학력 조건, 신청 직원의 현재 역할·활성·주인 담당, 항목별 최신 실제 통과 심사 결과를 검사합니다. 시드의 확인 플래그만으로 파일을 만들지 않습니다.
- 새 파일은 schema_version=3, member_id, recipient_id, grant_id, match_id, purpose=introduction, scopes, fields입니다. fields는 선택된 검토 결과·검토 시각만 포함하며 원본·실명·연락처·학교·회사명은 포함하지 않습니다.
- export_requests.purpose는 새 경로에서만 `matching_introduction`, consent_id는 matching_grants.grant_id입니다. 일반 업로드/기존 신청 API로 이 목적을 선택할 수 없습니다. 기존 자료 형식·행은 변환하지 않습니다. 새 테이블·컬럼·데이터 마이그레이션은 없습니다.
- 반출 승인과 다운로드에서 매칭·동의의 현재 유효성, 주체·수신자·범위·기간, 내부의 현재 심사·담당 권한, 고정된 파일·버전·해시를 재확인합니다. 철회·동의 교체·만료·관계 종료 후 기존 새 경로 파일은 다시 받을 수 없습니다. 이미 다운로드한 사본은 회수할 수 없습니다.
- 외부 이용 현황은 심사→소개→신청·수락→공개 동의→일정·승인 자료의 다음 행동을 안내합니다. 공개 동의 탭은 매칭 동의를 먼저 보여주고 기존 별도 동의의 조회·철회를 유지합니다. 새 동의 작성은 매칭 현황에서 진행합니다.
- 외부에서 실제 결제, AI/OCR, 원본 자동 마스킹, 사진·연락처 제공을 추가한 것은 아닙니다. 직원 일정과 회원 회신 경로는 유지합니다.

적용·브라우저 확인 순서는 [20명 환경 안내의 업무 흐름 업데이트](internal20-start-guide.md#매칭동의파일-제공-업무-흐름-업데이트)를 따릅니다. Docker와 실제 브라우저의 새 흐름 확인은 사용자 PC에서 수행해야 합니다. GitHub push는 별도 확인 후 진행합니다.
